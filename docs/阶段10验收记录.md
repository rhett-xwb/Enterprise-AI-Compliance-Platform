## 3 新增针对性验证

| 场景 | 工程证据 |
| --- | --- |
| 重复请求/消息 | 一个 parse task/job，重复消息只有一次 parser 调用和一套来源 |
| 事务回滚 | REQUIRES_NEW 回滚同时移除业务 task 和 outbox |
| broker 未确认/故障 | outbox 保留 PENDING；确认后长期未消费仍允许补发 |
| 发布确认 | mock 正 confirm 才标已发送；抛错、nack、returned 均保留待发 |
| OCR 临时故障 | PARSER_UNAVAILABLE 落库等待，新 token 重试成功；旧消息无调用 |
| 重试上限 | 三次自动处理后 FAILED，人工至累计五次，再拒绝；永久错误直接 FAILED |
| 消费者退出恢复 | 模拟过期租约重新入队、丢弃旧解析响应；已提交成功结果收敛 job SUCCEEDED；升级模式接管无 outbox 的过期旧解析任务 |
| 索引重复/重试 | 同一 generation 与 payload keys，重试后一套 chunk，重复消息不再调用向量服务 |
| 删除 | 删除后消费不调用 parser，缓存存在时仍不能从业务接口读取 |
| 缓存治理 | 本人命中，非本人被拒且不访问缓存；同一账号失去 document:manage 后原 JWT 请求被拒 |
| Redis 客户端 | namespace/version/hash key、五分钟 TTL 参数、序列化契约、异常回源、关闭不连接 |
| 消息格式 | 无效 JSON 拒绝至死信策略；合法消息调用 durable processor |
| 管理权限 | 非 ADMIN 的监控列表/metrics 返回 403；ADMIN 可读取，输出不含 payload/run token |

这些验证分别证明数据库行为和客户端契约；不证明真实网络故障、broker 持久化、Redis 服务端 TTL 或 Qdrant 重复 upsert 已通过。
