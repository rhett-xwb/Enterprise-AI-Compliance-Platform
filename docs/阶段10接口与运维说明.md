# 阶段十：缓存、异步任务与故障恢复

日期：2026-10-12。代码与工程验证见[验收记录](阶段10验收记录.md)。真实 RabbitMQ/Redis、缓存性能与断电演练需要单独验收；默认不开启新中间件。

## 1 处理模式与事务边界

`ASYNC_TASKS_ENABLED=false` 保留解析数据库轮询和同步索引。启用后，解析与索引均由 RabbitMQ 驱动，关闭原解析轮询，HTTP 只准备任务。解析仍返回 202；索引保持现有 200/state 接口，PROCESSING 包含排队/执行，前端轮询。解析和索引分别由治理者明确发起，解析成功不会自动索引或发布。

```text
授权 + 锁制度 → 本地事务保存业务任务和 document_async_job → COMMIT
→ dispatcher 查询已提交 outbox → 持久消息 → broker confirm + 无 returned
→ 标记 dispatched_at → listener → 数据库 claim + 租约 → 调用解析/向量服务
→ 原有来源/切片结果事务 → job 成功/重试/失败落库 → ACK
```

`document_async_job` 同时是 outbox 和任务账本，没有把消息投递放进业务事务。RabbitMQ 断开时业务入队可成功，任务保留 PENDING/BROKER_UNAVAILABLE；10 秒后重新投递。不将 broker 故障计入业务处理次数。确认后但未消费的 PENDING 每 60 秒允许补发，以覆盖队列丢失或确认边界异常。消息只含 job id/message token，不携带正文、原件路径、用户令牌或密钥。持久 durable 队列为 `compliance.document.tasks`，无效消息到 `compliance.document.dead`；坏消息不能反复堵住正常消费。

参考：[RabbitMQ confirms/ack](https://www.rabbitmq.com/docs/confirms)、[可靠性与重复投递](https://www.rabbitmq.com/docs/reliability)。交付是至少一次投递，业务侧实现幂等，不承诺跨数据库/向量库的分布式原子提交。

## 2 幂等、重试与租约

| 项目 | 策略 |
| --- | --- |
| 解析键 | `parse:<version>`；同一版本一条 job/parse task |
| 索引键 | `index:<version>:<generation>`；payload 固定 generation 和 vector keys |
| 重复消费 | document 锁后 job 行锁；只接受 PENDING + 当前 message token；PROCESSING/SUCCEEDED 与旧消息均不重复执行 |
| 自动重试 | 仅临时故障，累计前三次处理内自动重试；等待 5/10 秒，落库后重新投递 |
| 人工重试 | FAILED 且累计小于 5；原 job/代次重用，次数不清零 |
| 永久故障 | 加密文件、无正文、解析响应校验失败等直接 FAILED，人工检查后再试；索引异常统一 INDEX_UNAVAILABLE 有限重试 |
| 消费租约 | 600 秒；解析客户端配置最大 500 秒；索引 HTTP 上限 180 秒 |
| 宕机恢复 | 租约超时先检查业务结果已提交则收敛 SUCCEEDED，否则按次数重试/失败 |
| 迟到响应 | 解析沿用 run_token；索引沿用 generation、稳定 keys 与原有删除/停用校验 |
| 新代次隔离 | 被新 generation 替代的历史索引 job 不可重新激活新索引 |

索引外部 upsert 已成功但数据库提交失败时，重试使用相同 keys，避免创建多套向量。运行中删除/停用仍由原 Store 完成时检查，不会把迟到结果发布为有效制度。使用 MySQL 的授权/current version/generation 过滤检索，不能依赖向量 payload 中的旧权限快照。

升级启用时，dispatcher 收养尚未入账的 PENDING 解析任务，以及原租约已经过期的旧 PROCESSING 解析任务；不抢占租约仍有效的旧任务。旧同步索引没有完整持久 payload，超时后由治理者重新发起。运行中的索引切换处理模式应先停止接收新任务并排空，避免切换时并存两种 worker。

## 3 Redis 策略与测量

本阶段只提供可选解析结果缓存；默认 `SOURCE_CACHE_ENABLED=false`。**没有缓存问答答案、搜索结果、身份、角色、制度有效集合或审批材料**。没有实际 Redis 基准证据前，不认定开启缓存能改善性能。

- 每次 sources 请求先在 MySQL 重新检查本人/ADMIN 治理权限和未删除制度，随后确认解析 SUCCEEDED；命中不能绕过授权。
- key：`<CACHE_NAMESPACE>:sources:v1:<versionId>:<sha256>`，不可变原文件与成功解析绑定。不同数据库必须使用不同 namespace。
- TTL 5 分钟；只在读取事务提交后写缓存，回滚不能污染外部缓存。
- 序列化正文超过 256,000 个字符不写入；Redis 最大 128MB、allkeys-lru，仅作可丢弃加速层。
- Redis 连接/读写上限各 500ms，异常回源 MySQL；缓存错误仅计数，不返回客户端故障堆栈。
- 删除后缓存可能保留至 TTL，但业务入口先授权/检查删除，不能读取；Redis 本身必须作为私有敏感数据设施管理。
- 当前 metrics 是单个 Java 进程累计，重启清零，不代表 Redis 全局统计。

可复现测量工具：`scripts/measure-stage10-cache.ps1`。准备已成功解析版本，以授权治理账号设置 BENCHMARK_USERNAME/PASSWORD，分别在关闭与开启缓存时各跑 50 次，记录中位数、P95、平均延迟及 cache hits/misses/errors。在相同服务/正文/并发下比较，长正文不得仅以短样例代替；再执行角色撤销、删除、Redis 断开与重连。工具从真实 API 测量授权和网络成本，本次未执行 Redis 对照实验。按结果决定是否开启及缓存对象，不用契约测试冒充性能测量。

## 4 管理接口与页面

所有 `/api/document-tasks` 接口同时在 SecurityConfig 和方法级限定 ADMIN，法务与员工返回 403。

| 接口 | 内容 |
| --- | --- |
| GET `/api/document-tasks` | 最近 100 条任务，类型/状态/次数/错误/时间；排除 payload、message/run token |
| GET `/api/document-tasks/metrics` | 按类型/状态全量计数、最早创建时间、运行模式和本进程缓存计数 |
| POST `/api/document-tasks/{id}/retry` | 异步启用时重新排队合法失败任务；记录 ASYNC_RETRY 审计 |

管理员菜单“文档处理任务”支持加载、空状态、服务失败与刷新恢复、有限人工重试。治理者继续使用制度管理的解析/索引窗口，索引 PROCESSING 自动轮询。

## 5 启动与恢复

先配置独立随机 `RABBITMQ_PASSWORD` / `REDIS_PASSWORD`，中间件模板不含默认密码：

```powershell
docker compose --env-file .env -f docker/middleware.compose.yml up -d
docker compose --env-file .env -f docker/middleware.compose.yml ps
```

RabbitMQ/Redis 只暴露本机端口；Rabbit 固定 hostname，数据保存独立 volume；Redis 数据不需持久化。Rabbit 登录用户、端口/vhost 与 Java 环境变量必须匹配。不同数据库部署必须使用独立 Rabbit 实例/vhost 和不同 Redis namespace，避免两个环境共享相同任务队列。启用 `ASYNC_TASKS_ENABLED=true`，继续配置原 PARSER_*/RETRIEVAL_* 与共享私有文件目录；Spring 不自动读取根 `.env`，按原启动说明注入进程环境。缓存独立按测量决定 SOURCE_CACHE_ENABLED，不以启用 RabbitMQ 为前提。模板版本固定，本机没有 Docker，模板和镜像启动未验收。

故障检查顺序：MySQL job/error/next_attempt → 服务启用状态 → broker/队列与消费者 → parser/retrieval → 制度版本与来源。BROKER_UNAVAILABLE 时先恢复 broker，自动补发；临时业务故障自动重试三次后 FAILED，再恢复依赖并人工重新排队；第五次失败应修正文档/服务后创建新版本，不重置数据库次数。死信仅用于格式非法消息，不代表业务 FAILED，也不可直接把未经核对的死信回放为业务任务。

关闭：`docker compose --env-file .env -f docker/middleware.compose.yml stop`；不要通过删除 volume 处理积压。已确认投递但未消费的 DB 任务可补发，不把 Rabbit 数据持久化等同于集群高可用。长期任务归档、集中指标/告警、MQ TLS/集群、Redis HA、生产故障演练留到部署阶段。
