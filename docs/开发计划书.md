# 企业智能法律合规与审批平台开发计划书

项目名称：Enterprise AI Compliance Platform  
计划版本：1.0  
编制日期：2026年10月11日  
编制依据：[企业智能法律合规与审批平台开发流程说明](./企业智能法律合规与审批平台开发流程说明.docx)

本计划用于组织项目设计、模块开发、联调和交付验收。先完成业务基础，再接入 AI，每个阶段以可验证的交付物结束。下列任务清单表示计划与验收要求，不表示功能已经实现；实际完成记录和验证结果维护在 [开发日志](./DEVELOPMENT_LOG.md) 中。

## 1 项目目标

面向企业法务与合规部门、普通员工和管理审批人员，建设企业内部合规管理平台，形成以下业务闭环：

```text
制度管理 → 文档解析 → 制度问答 → 员工申请 → AI 预审 → 人工审批
```

AI 提供有依据的分析和修改建议。检索依据不足时明确说明无法判断，最终审批决定由有权限的人员作出。合同审查作为后续业务增强，不替代核心申请审批闭环。

## 2 交付范围

| 交付层次 | 主要内容 | 完成要求 |
| --- | --- | --- |
| 基础版本 | 用户认证与 RBAC、制度文档上传和版本管理、OCR、带引用的制度问答、员工申请提交 | 基础功能可联调，制度来源和访问权限可验证 |
| 完整业务版本 | AI 申请预审、风险提示、修改建议、可配置人工审批、审批留痕 | 一笔申请可从提交走到人工处理结果，并保留完整依据 |
| 提升版本 | 合同审查、缓存、异步任务、部署优化 | 根据业务与测量结果完善能力，并验证一致性和恢复能力 |
| 可选扩展 | 微服务拆分、Elasticsearch、多租户 | 核心闭环稳定后另行评估范围与必要性 |

## 3 角色与权限

| 角色或职责 | 主要操作 |
| --- | --- |
| 普通员工 | 查询授权制度、维护申请草稿、查看预审与审批结果 |
| 法务与合规人员 | 管理制度与版本、检查解析结果、处理法务审批和合同审查 |
| 系统管理员 | 管理用户、角色、权限、组织和系统配置 |
| 主管与财务等审批职责 | 按流程分配处理待办，可由具备相应权限的用户承担 |

系统角色控制功能权限；部门、文档访问范围和流程任务归属控制数据权限。用户与角色采用多对多关系，不能仅用一个 `role_id` 表达全部审批职责。

## 4 架构与数据职责

建议采用模块化 Spring Boot 后端，Python FastAPI 单独承担 OCR。RAG 编排由一个服务负责，Spring AI 与 LangChain4j 二选一；如果改由 Python 承担 RAG，应同步调整接口与责任边界。具体依赖版本在初始化时验证并固定。

规划目录如下，各目录按实际开发阶段建立：

```text
Enterprise AI Compliance Platform/
├── backend/       Java 业务后端
├── frontend/      Vue 前端
├── ai-service/    Python 文档解析服务
├── docs/          设计 计划 日志与验收资料
└── docker/        部署配置
```

核心数据域包括用户、角色、权限与部门；文档与版本、解析任务、文本块与索引状态；申请、流程配置、流程实例、任务与操作记录；问答会话、消息、引用与 AI 分析记录。MySQL 保存业务事实，向量数据库保存可重建的检索索引。

## 5 开发顺序与阶段计划

总体顺序为：范围与设计 → 工程骨架和数据模型 → 基础后端 → 认证权限 → 前端基础 → 文档管理 → OCR → RAG → 制度问答 → 智能审批 → 工程化与完整验收。

### 阶段 4 文档与版本管理

**目标**：让制度成为可治理、可追溯的业务资产。

**任务**：

- [ ] 支持 PDF、Word 和图片上传，验证类型与大小。
- [ ] 存储原文件与元数据，建立文件存储抽象。
- [ ] 管理版本、适用范围、生效时间和发布状态。
- [ ] 建立发布、失效和操作日志机制。

**交付物**：文档接口与页面、文件存储抽象、版本模型、发布与失效规则。

**验收**：可以上传和查询版本；授权用户可以查看文件，未授权下载被拒绝；发布新版本后旧版不再用于当前制度问答。

**设计约束**：逻辑文档与不可变版本分开。逻辑文档保存制度身份，版本保存原文件、版本号、发布时间和内容。发布状态与处理状态分别维护。删除或失效后应使检索不可见，并按约定保留历史审计。

### 阶段 5 文档解析服务

**目标**：提取可用于检索且能定位来源的文本。

**任务**：

- [ ] 使用 FastAPI 封装解析接口。
- [ ] 电子 PDF 优先提取文本，扫描件和图片调用 PaddleOCR。
- [ ] Word 使用文档解析工具处理。
- [ ] 限制页数、大小和并发，处理超时与失败。
- [ ] 建立任务状态、错误码与幂等重试机制。

**交付物**：解析服务、请求与响应契约、任务状态、错误码、解析样例。

**验收**：电子 PDF、扫描 PDF 和图片可以返回文本与页码；错误文件得到明确失败结果；失败任务可以重试且不重复生成数据。

**建议契约**：Java 以 `documentVersionId`、`taskId` 和受控文件引用发起任务；返回 `pages`，每页包含 `pageNumber`、`text` 和可选的块坐标、识别置信信息。Python 服务仅由内部业务服务调用，不接受任意公网地址下载。

**处理链路**：

```text
上传版本 → 创建解析任务 → 提取文本或 OCR → 清洗并保留页码
→ 切片与索引 → 法务检查 → 发布生效
```

解析或索引失败时保持不可问答状态；重试成功后再进入发布检查。低质量扫描件提供人工检查入口，不将空文本当作成功。原文件、页码与文本块保持关联。Word 未建立固定版式时引用段落或章节，不编造页码。权限或发布状态变化后，检索与答案缓存应及时应用新规则。

### 阶段 6 RAG 检索基础

**目标**：建立可控制版本与访问范围的知识检索。

**任务**：

- [ ] 按标题与条款切片，并设置适当重叠。
- [ ] 接入 Embedding，选择并固定向量数据库。
- [ ] 保存文档身份、版本、页码、章节、访问范围与文本块标识。
- [ ] 实现检索过滤、索引重建与失效机制。

**交付物**：切片方案、索引服务、检索接口、索引重建与失效机制。

**验收**：固定问题集能够找到相关原文；旧版本、未生效和未授权内容被排除；重复索引不会产生重复有效条目。

**知识域规则**：区分企业制度、法律法规和合同模板。员工制度问题优先检索企业制度；合同审查按权限组合相关知识域。法规需另行维护来源、适用范围与有效性，初期不默认具备完整法规覆盖。

### 阶段 7 制度问答

**目标**：让答案具有可核对的制度依据。

**任务**：

- [ ] 先检索，再构造受约束的提示词并调用模型。
- [ ] 将检索内容视为资料，返回答案和引用。
- [ ] 保存问答记录，提供来源查看与历史记录。
- [ ] 对无依据、冲突内容和模型失败提供明确结果。
- [ ] 建立项目专用问题集与质量评估记录。

**交付物**：问答 API 与页面、来源查看、历史记录、质量评估样例。

**验收**：正常问题返回有效引用；无资料时说明依据不足；跨权限问题不会泄露内容；模型失败时页面可以恢复。

**引用规则**：引用包含文档名称、版本、文本块标识、章节或页码和引用片段。引用由服务端从实际检索结果中组装，并验证答案中的引用标识确实存在。历史答案保留当时版本；打开来源时重新校验权限，失效版本明确标识。

**质量评估**：问题集覆盖正常问答、无答案、旧制度、权限边界、条款冲突和文档内恶意指令。分别评估条款召回、答案符合程度和引用定位，保存问题、预期依据、实际回答与失败原因。核心演示问题逐条人工核对；权限泄露和引用不存在是阻断性问题。准确率目标在明确文档样本后约定，不用模型自评代替人工核对。召回不佳时先检查文本、切片与检索，再调整提示词。

**模型依赖管理**：通过环境变量或密钥管理注入配置，不提交真实凭据。记录模型与 Embedding 标识、耗时和失败类型。更换 Embedding 时评估索引重建；超时与限流提供重试或明确错误。模型调用失败不能生成“审批通过”的默认结果。

### 阶段 8 员工申请与 AI 预审

**目标**：让员工在正式提交前发现缺项和制度风险。

**任务**：

- [ ] 实现申请草稿、表单、附件与提交记录。
- [ ] 按确定的首条业务流程实现申请页面；差旅为候选。
- [ ] 金额与必填项使用确定性规则检查。
- [ ] AI 根据授权制度提供解释与修改建议。
- [ ] 支持修改、再次预审和旧分析结果失效。

**交付物**：申请页面与接口、结构化预审结果、修改与再次预审功能。

**验收**：申请可以保存、修改和提交；风险关联依据；修改金额或附件后旧预审结果标记失效；提交关联当前申请内容。

预审结果包含分析状态、风险级别、问题清单、制度引用、修改建议、申请内容版本和分析时间。金额示例仅作为测试数据，正式阈值来自配置或有效制度。缺少规则或依据时返回无法判断，AI 风险等级不能直接改变人工审批决定。

### 阶段 9 可配置人工审批

**目标**：完成员工到审批人的业务闭环。

**任务**：

- [ ] 在阶段 0 比较直接接入 Flowable 与有限范围的可配置方案，并在实现前确定选型。
- [ ] 明确节点、条件、审批人选择、流程版本与发布规则。
- [ ] 实现待办、同意、拒绝、退回、撤回与历史记录。
- [ ] 实现服务端状态校验、任务归属校验及并发防重。

**交付物**：流程配置、申请状态与流转规则、审批中心、审计记录。

**验收**：不同金额按配置进入对应节点；无审批人时提示配置问题；非任务处理人无法审批；并发或重复提交不会重复流转。

**选型约束**：需要可视化建模、复杂分支和流程迁移时优先评估 Flowable。有限流程方案仅支持明确约定的节点与条件，不承诺完整 BPMN 能力；不能以写死的金额判断替代可配置流程。

**状态与审计**：申请状态建议为草稿、已提交、审批中、已通过、已拒绝、已撤回。退回修改需另行定义状态与恢复路径，AI 分析状态独立维护。记录审批意见、处理人、时间、动作和前后状态。流程发布生成版本，运行实例固定引用启动版本，配置调整不静默改变旧实例。审批完成后保留申请快照与预审依据；修改中的申请重新确认后才能再次进入审批。

### 阶段 10 缓存与异步处理

**目标**：改善文档处理体验并保持一致性。

**任务**：

- [ ] 按测量结果引入 Redis。
- [ ] 使用 RabbitMQ 承载解析与索引任务。
- [ ] 设计幂等键、重试次数、失败记录与人工重试入口。
- [ ] 提交事务后可靠投递任务，明确补偿或 outbox 方案。

**交付物**：缓存策略、异步任务链路、失败恢复与监控说明。

**验收**：重复消息不会重复索引；OCR 服务故障后任务可以恢复；制度或权限变化后不会返回不适用的缓存答案。

答案缓存至少区分访问范围、有效制度或索引版本、问题与模型配置；初期可以只缓存低风险元数据。数据库状态与消息投递需有一致性方案，避免上传成功但任务丢失。

### 阶段 11 部署与完整验收

**目标**：交付可以复现的演示系统。

**任务**：

- [ ] 编写 Docker 配置与环境变量示例。
- [ ] 提供数据库迁移、演示账号和制度样本。
- [ ] 编写启动、停止、备份与故障排查说明。
- [ ] 检查健康状态、日志与密钥配置。
- [ ] 执行完整业务演示，形成验收报告。

**交付物**：部署说明、演示脚本、验收报告、已知限制、运行截图。

**验收**：新环境按说明可以启动；真实文件可以解析并问答；员工申请经过 AI 预审与人工审批形成完整记录。

## 6 后续合同审查增强

在申请闭环稳定后增加合同解析、规则检查、风险条款定位和修改建议。先明确合同类型和审查规则，再设计评估样本。每条风险关联原合同位置与适用依据，由法务复核后采用。

## 7 完整验收与进度管理

| 验收范围 | 必须取得的证据 |
| --- | --- |
| 身份与权限 | 登录、令牌过期、越权接口、跨用户资源访问验证记录 |
| 文档与解析 | 上传、发布、旧版失效、OCR 失败重试、文本定位结果 |
| 检索与问答 | 固定问题集、实际引用、无答案与权限隔离验证结果 |
| 申请与审批 | 修改后预审失效、不同分支、重复审批、完整操作历史 |
| 运行与交付 | 新环境启动步骤、配置示例、演示数据、完整业务演示 |

按依赖关系逐阶段推进，暂不设定缺乏依据的工期。每阶段先估算任务量，再根据实际完成速度更新计划。基础版本验收后进入完整业务版本，核心问题修复后再推进架构扩展。

阶段完成需同时满足：功能可以演示，关键异常可以处理，必要检查通过，文档已同步。仅有页面或模拟接口返回不计为业务闭环完成。

## 8 Codex 协作与变更管理

每次任务按以下流程推进：

```text
明确范围 → 阅读相关代码和项目约定 → 给出具体改动方案
→ 实现可验收任务 → 执行适当检查 → 前后端联调 → 更新文档 → 汇报结果
```

在已授权范围内持续完成工作。架构决策和新增范围由项目负责人确认，每次任务明确业务场景、允许修改的模块、接口契约、异常处理、验收条件及范围外内容。任务以能够完成并核对为准。

### 可复用任务模板

```text
任务：实现【模块中的具体能力】。
业务场景：【角色在何种条件下做什么】。
前置条件：【已有数据、接口和配置】。
```

### 任务示例

实现制度新版本发布。法务选择已解析并已索引的版本进行发布，校验权限和生效条件，在一致的业务操作中更新当前有效版本。当前检索排除旧版，历史问答保留旧引用并标识状态。验证未完成解析不能发布、未授权用户不能发布、重复发布不会出现两个冲突的当前版本。

### 质量规则

- 业务条件以接口和服务端校验为准。
- 关键权限、版本过滤、任务幂等和审批状态流转执行有针对性的验证。
- 普通可逆样式调整以构建和视觉检查为主。
- 提交前检查差异，避免混入无关重构。
- 技术方案变化同步更新数据模型、接口与验收说明。
- 每次重大改动同步更新开发日志，记录实际结果和遗留事项。
