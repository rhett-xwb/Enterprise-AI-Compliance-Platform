# 阶段八学习笔记：让差旅申请带着当前内容和预审依据进入人工处理

日期：2026年10月12日  
主题：申请草稿、内容版本、附件、确定性规则、AI 建议、并发控制与提交快照。

## 1 阶段目标与生活场景类比

用户确定首条流程为差旅申请。员工填写目的地、起止日期、事由和人民币金额，保存草稿、添加附件、预审，再确认当前内容提交。阶段八完成申请入口与提交留痕，人工审批流由阶段九继续实现。

生活类比：你在窗口填出差单。工作人员先检查日期是否倒写、金额是否漏填；制度顾问再根据你有权阅读的规定提出建议。你改了预算或换了发票，顾问之前盖的“已检查”章就不能继续代表新材料。正式递交时，窗口复印整套材料并保存检查记录，避免以后拿修改后的材料解释当时的申请。

**有什么用**：把“AI 说了些什么”变成“针对哪一版申请、依据哪些制度、什么时候分析、提交的究竟是什么”。

## 2 为什么先做草稿，再做预审，最后做提交

```text
阶段四至六：制度版本 → 真实解析 → 授权有效原文检索
阶段七：依据生成、引用校验与历史权限复查
阶段八：草稿 → 附件 → 内容版本 → 规则与 AI 预审 → 当前内容快照提交
阶段九：按流程版本创建人工待办、处理与审计
```

预审先要知道申请内容；提交先要知道预审针对哪个版本；审批先要有稳定的提交材料。Java 后端类比：先建立聚合根和数据约束，再组合外部服务，最后实现状态迁移和审计。

阅读入口：[TravelController.java](../backend/src/main/java/com/enterprise/compliance/request/TravelController.java)、[TravelStore.java](../backend/src/main/java/com/enterprise/compliance/request/TravelStore.java)、[TravelReview.java](../backend/src/main/java/com/enterprise/compliance/request/TravelReview.java)。

## 3 草稿与提交是不同的校验时机

草稿允许缺目的地、日期、事由或金额，方便先记下想法；非法负数、超过两位小数、超长字段仍被接口校验拒绝。预审把缺项列成 issues；提交必须再次调用确定性 rules 检查，而不能相信前端按钮是否禁用。

| 检查 | 实现与意义 |
| --- | --- |
| 标题、目的地、事由 | 非空才可提交 |
| 起止日期 | 两个日期完整，结束不早于开始 |
| 金额 | 人民币，大于零；不让模型做基础算数与字段校验 |
| 业务金额上限 | TRAVEL_MAXIMUM_AMOUNT 默认 0 表示不开启，配置正数后检查；配置不是引用制度 |
| 附件 | 类型、签名、大小、数量与本人归属；当前不解析正文 |

Java 类比：Bean Validation 守住输入格式，Service 的业务规则决定状态迁移，二者不能互相代替。演示中的 1000 元、2345 元只是测试金额，不是公司制度阈值。

**后续怎么用**：增加费用明细或业务字段时，先明确可验证规则与制度要求，把后端提交校验作为最终入口。真实上限由管理员根据业务核实后配置。

## 4 contentVersion：检查意见必须对应材料版本

新草稿版本 1。修改表单、添加附件、移除附件，每次版本加一，同时将旧分析状态标记 STALE。客户端提交修改时带 contentVersion，服务端核对它与数据库当前版本是否相同。

项目例子：版本 1 金额 1234 元并已预审；改为 2345 元后成为版本 2，旧预审失效；添加 travel.pdf 后成为版本 3，版本 2 的预审再次失效。必须检查版本 3 才能提交。

Java 类比：类似 `@Version` 的乐观版本检查；这里还使用 `SELECT ... FOR UPDATE` 锁住申请行，把版本检查、修改、失效标记放进一个事务。不是依赖浏览器里的变量避免并发。

**有什么用**：两个浏览器同时操作时，旧页面修改不会静默覆盖新内容；金额和附件改变后，旧建议不会被误认为仍适用。

## 5 AI 预审如何工作

TravelReview 先获取本人草稿并执行 rules，再用阶段六检索找授权且当前有效的差旅制度，将表单与附件文件名交给阶段七 QuestionModel。模型返回 advice 和引用编号，服务端保存真实命中 evidence。

```text
读本人草稿与版本 → 规则问题
  → 授权制度检索 → 调用兼容模型 → 校验引用
  → 新事务锁申请并复核版本、全部依据 → 保存分析
```

模型调用耗时较长，放在数据库事务之外；返回后再核对材料和制度。类似调用支付平台后处理回调：请求开始时的订单状态不保证仍然有效。

| 结果 | 怎么理解 |
| --- | --- |
| REVIEWED / REVIEW_REQUIRED | 有依据建议，需人工核对；不代表风险低 |
| UNKNOWN | 生成关闭、没有依据或模型资料不足，明确无法判断 |
| CONFLICT | 报告条款冲突，至少两处引用，法务确认适用关系 |
| FAILED | 外部服务异常，记录失败码，可以重试 |
| STALE | 申请材料已改变 |
| RESTRICTED / SOURCE_OUTDATED | 制度来源撤权或不再有效，不能作为当前提交依据 |

HIGH 来自确定性表单问题，当前没有模型低/中/高风险分类器。AI 返回的是解释与修改建议，不直接决定审批结果。无依据但表单规则正确的申请可以提交，保留无法判断的记录供人工处理；失败记录不能当作完成预审。

**当前边界**：真实模型仍按阶段七约定待配置和人工质量验收。受控响应只证明协议、引用和链路；引用编号存在不证明语义正确。附件只保存元数据，不宣称已识别或审查附件正文。

## 6 附件与引用为什么都要保留快照

附件复用私有本地存储，记录随机键、文件名、SHA-256、大小和类型，客户端不直接访问物理路径。SHA-256 像材料指纹，用于说明保存的文件内容。提交快照保存当时活动附件集合，移除的附件不再参与后续提交。

制度依据保存在分析 result_json 中，包含制度版本、当时文本块编号、原文与位置。阶段六重建索引会替换文本块，所以历史不能只依赖 chunk 外键。类似订单保存商品快照，商品表后来变化不应改写历史订单。

读取预审时重新检查全部输入依据：任一来源撤权/删除，隐藏全部建议与引用；旧版本仍授权时显示来源失效，必须重新预审才可提交。保存快照不意味着可以绕过当前权限。

**后续怎么用**：阶段九可以按 analysis_id 找到提交时的原文依据；审计工具仍需定义自己的授权范围。附件物理清理与留存期限后续制定，当前软移除保留历史文件。

## 7 提交是一个事务，不是单独改状态

提交检查当前版本、最新预审、规则和制度依据，然后同时完成：

1. request_submission 保存表单、币种、附件和 reviewId，唯一 request_id 阻止重复。
2. approval_request 状态改为 SUBMITTED。
3. approval_action 记录本人 SUBMIT、前后状态与时间。

任何一步失败，整个数据库事务回滚。提交后拒绝表单修改、附件增删和再次预审。

Java 类比：下单要同时保存订单头、订单项和支付意图，不能只改一个状态。数据库行锁协调修改与提交；并发验收验证这两种操作不能同时成功。

入口：[V8__travel_requests.sql](../backend/src/main/resources/db/migration/V8__travel_requests.sql)。V8 扩展附件 MIME/软删除，增加提交表，使用预留申请、分析和动作表。没有新增工作流实例、审批待办或批准逻辑。
