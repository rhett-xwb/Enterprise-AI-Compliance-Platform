# 阶段 5 学习笔记

主题：文档解析、OCR、持久任务与可追溯正文  
日期：2026年10月12日

阶段目标：把制度原文件变成能定位来源的文字，让失败可以解释、任务可以重试，并为下一阶段的切片与检索准备输入。

延续企业办事大厅的类比：阶段四建立了档案室，保存每个版本的原件；阶段五增加档案整理员。电子档案可以直接抄录正文，扫描件要先识字。整理员不仅交出文字，还要注明“第几页”或“第几段”，并留下任务登记。

## 1 为什么先解析，再做向量检索

```text
阶段 4：不可变原文件、版本、访问范围
   ↓
阶段 5：正文提取/OCR、页码或段落、任务状态
   ↓
阶段 6：切片、Embedding、向量索引
   ↓
阶段 7：检索依据、模型回答与引用
```

Embedding 是把文字转换成便于相似检索的数字表示。没有正文就无法做可靠切片；没有版本和来源，找到一段文字后也无法回答它出自哪份制度。

本项目例子：扫描差旅制度识别出“出差前必须提交审批申请”，同时保存版本 ID 和第 1 页。阶段六可以将这段文字切成检索块，阶段七再把来源作为引用依据。

**有什么用**：先解决输入质量与来源，再接入模型，后续回答才能核对原件。

**当前边界**：解析不是问答，也不是索引。阶段五成功后显示 PARSED（已解析，待索引），仍不能发布。

## 2 文本提取和 OCR 是什么

文本提取是读取文件里已有的字符；OCR 是从像素图像识别文字，英文全称 Optical Character Recognition。

生活类比：电子 PDF 像可复制的电子邮件，扫描件像给纸张拍了一张照片。前者直接读取字，后者要识别图片上的笔画。

| 文件 | 本项目处理 | 来源 |
| --- | --- | --- |
| 电子 PDF | PyMuPDF 读取文字层，包括短正文 | 真实页码 |
| 无文字层的扫描 PDF | 逐页渲染图片，再用 PaddleOCR | 真实页码 |
| PNG/JPEG | PaddleOCR 中文识别，处理图片旋转元数据 | 第 1 页（图片） |
| DOCX | 解压 OOXML，按正文与表格段落读取文字 | 段落顺序、可识别标题 |

Java 后端并不适合承担所有 OCR 库的集成，所以把 Python 擅长的文档与模型能力封装成 FastAPI 内部 HTTP 服务；Java 继续负责身份、权限、业务状态和 MySQL。

**后续怎么用**：合同、法规原文也可以复用提取能力，但不能直接复用制度权限；需要先建立各自的业务授权。

## 3 FastAPI 与 Spring Controller 如何类比

FastAPI 是 Python 的 HTTP 服务框架。在本项目中，`@app.post('/internal/parse')` 类似 Spring 的 `@PostMapping`；Pydantic 模型类似带参数校验的 Java DTO。

```text
Vue → Java ParsingController → MySQL 任务登记
                 ↓ Java 定时 worker
           ParserClient → Python FastAPI
                              ↓
                         文本提取/OCR
                 ← 带来源的 pages
            Java 校验并写入 MySQL
```

Python 不接收浏览器上传，也不查用户权限。它只接受 Java 给出的版本、任务、文件键、大小和摘要。用户只能操作自己有治理资格的制度；Python 通过内部共享密钥识别调用方。

**有什么用**：将技术能力与业务治理分开，未来更换 OCR 实现时，制度、账号和数据库逻辑不需要整体重写。

## 4 为什么接口只接受受控文件键

文件键是 Java 上传后生成的 UUID.bin，不是用户填写的磁盘路径或公网 URL。两个服务共享同一个私有文件目录，Python 仅在该目录中读取受控原件，并校验 SHA-256 与字节数。

生活类比：整理员根据档案室登记号领取原件，不允许来访者指定“到某台服务器任意下载一个文件”。Java 的 FileStorage 管理原件，Python 只负责读取和处理。

**有什么用**：防止路径越界、任意网络下载和处理错版本；摘要确保本次识别内容与上传时一致。

**怎么用**：Java/Python 配置相同的绝对 DOCUMENT_STORAGE_ROOT 和随机 PARSER_SECRET。相对路径受工作目录影响，两个服务可能看见不同文件夹，所以联调时使用绝对路径。

## 5 为什么不让浏览器一直等待 OCR

OCR 可能耗时较长。浏览器请求先登记任务，Java 返回 202，然后页面轮询任务状态。202 表示“已接受”，不是“已经成功”。

类比餐厅：前台接单后给你取餐编号，厨房稍后完成；前台不需要一直占着一个窗口等菜做完。

```text
POST parse → 返回任务编号
GET parse  → 排队中 / 解析中 / 成功 / 失败
GET sources → 成功后的页或段落正文
```

Java worker 使用 `@Scheduled` 定期领取 MySQL 中的任务；本阶段没有引入 RabbitMQ。任务保存在数据库，重启不会仅因为内存消失而丢掉登记记录。

**有什么用**：页面可以显示真实进度和失败原因；短 HTTP 请求不会被 OCR 长时间占用。

**当前边界**：这是数据库任务消费机制，后续并发量增加时再评估消息队列、调度与监控。上传后由管理者主动点击“开始解析”。

## 6 幂等、重试和运行令牌的区别

幂等是多次提交同一操作，最终不会重复生成业务数据。本项目使用唯一任务键 `parse:{versionId}`，同一版本始终复用同一个解析任务。

| 字段/机制 | 解决的问题 | 例子 |
| --- | --- | --- |
| task_key 唯一 | 连点提交不创建多个任务 | parse:42 |
| attempts | 记录真正领取执行了几次 | 失败后重试从 1 到 2 |
| run_token | 区分同一任务的不同尝试 | 每次执行新 UUID |
| lease_until | 发现崩溃留下的运行状态 | 到期后标记失败 |
| 版本/source_index 唯一 | 同一版本来源不重复保存 | 第 0 个来源只有一份 |

生活类比：取餐编号始终是 42，但重新做菜时厨房会换一张内部批次单。第一批迟来的菜不能覆盖已经完成的第二批。

Java 保存成功结果前核对任务状态与运行令牌；重试后旧响应不匹配，就丢弃。超过租约的 PROCESSING 在调度检查时标记 WORKER_TIMEOUT，需要管理者重试；最多五次失败，之后应检查并上传修正版。

**有什么用**：避免双击、网络重试或超时旧响应生成重复正文，或把新结果覆盖成旧结果。

## 7 事务和进程隔离分别保护什么

事务保护数据库一致性：正文来源与任务成功状态在同一个事务中提交。不能出现“任务显示成功，却只保存了半份正文”。同一制度的治理操作使用文档行锁，与阶段四发布和删除使用相同顺序。

进程隔离保护解析执行：Python 为每次文档处理启动独立子进程，超过默认 180 秒则终止它，释放并发槽位。仅给 Java HTTP 请求设置超时，不等于 Python 的 OCR 已经停止。

Java 类比：`Future.get(timeout)` 只代表调用者不再等，并不保证底层 native 模型已退出。独立操作系统进程可以被实际终止，适合限制耗时不确定的文件解析。

**有什么用**：一方面不留下半成品数据库记录，另一方面不会让超时任务长期占着识别资源。

**当前边界**：进程隔离与超时不等于完整操作系统资源沙箱。生产还需按容量设置进程/容器 CPU 与内存限制，正式环境压力尚未专项验证。

## 8 页码、段落和 OCR 置信度为什么要保存

页码与段落是来源位置，置信度是模型对识别结果的评分。两者用途不同：位置帮助找原文，评分帮助发现需要核对的内容。

PDF 有固定页；DOCX 可以因字体、打印机或排版改变分页，所以本阶段把 pageNumber 保存为 null，记录“段落 2”和标题，避免编造页码。表格中的段落也按文档顺序保存。

OCR 平均置信度低于 0.85 会显示“请人工核对”；空页保留 EMPTY_SOURCE，全文件没有文字则失败。前端用普通文本显示正文，制度文字中的 HTML 不会作为脚本执行。

**后续怎么用**：切片时继承版本、页码或段落定位；问答时通过这些信息打开有权查看的原文。高置信度也不能代替法务核对，扫描件可能把金额、否定词等关键文字识别错。

## 9 为什么新增独立来源表和 PARSED 状态

V5 新增 `document_parse_source`，保存提取后的原始来源；后续的 `document_chunk` 保存用于检索的切片。一页可能拆成多个块，若混用同一表，就会把“原始来源”和“检索组织方式”绑在一起。

```text
原文件 → document_parse_source（页/段落）
              ↓ 阶段 6
         document_chunk（切片与索引）
```

版本处理状态增加 PARSED，清楚表达“解析完成、索引没完成”。Flyway 通过 V5 增量迁移，不修改已经应用的 V1–V4。阶段四的 READY 和完整索引发布检查继续保留。

**有什么用**：不会把真实解析成功误写成知识库已就绪；未来调整切片策略时可以从保存的来源重新组织文本。

## 11 本次验证与下一阶段

本次实际完成前端构建、隔离 V1–V5 空库迁移、10 个 Python 测试、26 个后端测试和 14 个 Chromium/HTTP 用例，均通过。真实 PaddleOCR 识别扫描 PDF、PNG/JPEG 中文样例，电子 PDF 与 DOCX 也完成真实链路；损坏文件失败重试未生成部分或重复来源。桌面与移动端来源窗口已截图核对。
