# 阶段 2 学习笔记

主题：用户认证、角色权限与资源访问控制  
日期：2026年10月12日

这阶段完成的是后端的身份与权限体系：确认访问者是谁，判断他能执行哪些操作，以及能查看哪些数据。

延续阶段 1 的企业办事大厅类比：阶段 1 建好了大厅、档案和办事窗口；阶段 2 为员工发放通行证、规定岗位权限，并检查每个人可以调阅哪些档案。

## 1 为什么把这些放在第二阶段

开发顺序依据模块之间的依赖关系确定。认证需要阶段 1 已建立的用户表、角色关系、密码散列、数据库连接和统一异常处理；后续页面与业务又需要认证提供当前用户和权限。

```text
阶段 1：工程能运行，用户和角色数据能存取
   ↓
阶段 2：确认当前用户，限制操作和数据访问
   ↓
阶段 3：前端对接登录、身份、菜单和错误处理
   ↓
后续阶段：文档、OCR、知识库问答、申请与审批
```

例如，后续法务上传制度时，需要记录上传人，并检查是否有文档管理权限；员工提交申请时，申请人应来自登录身份；AI 检索制度时，也要限定用户可以访问的文档。

如果先实现这些业务，再增加权限，就需要逐个修改接口、查询和测试，补上原本缺少的身份与访问规则。

**有什么用**：先建立各模块都依赖的访问基础，后续业务可以按统一方式使用身份和权限，减少重复设计和返工。

**为什么不放在第一阶段**：第一阶段先验证请求、业务、数据库和响应的完整链路，并使用受控的临时认证。第二阶段在这个可运行基础上实现正式账号认证，便于分别定位基础读写问题和权限问题。

**当前边界**：阶段划分是本项目的实施安排，并非所有项目都必须采用相同编号。大型团队也可以并行设计前端与权限，但上线业务仍需要可靠的访问控制。

## 2 认证与授权的区别

认证是确认身份，授权是判断该身份能否完成某项操作。

| 概念 | 要回答的问题 | 本项目例子 |
| --- | --- | --- |
| 认证 | 你是谁？ | 用户名与密码正确，登录成功 |
| 操作授权 | 你能做什么？ | 员工不能管理用户，管理员可以 |
| 资源访问控制 | 你能操作哪份数据？ | 员工可以读本人申请，不能读其他员工申请 |

工作场景中，刷员工卡进公司对应认证；是否可以进入财务室对应授权；进入财务室后是否可以查看某个人的报销材料，还需要检查数据范围。

在 Java 后端中，这些判断发生在请求处理链和业务访问过程中。登录成功并不代表后续所有接口都允许访问。

**有什么用**：把身份、操作资格和数据范围分别说明清楚，避免只检查“已登录”就放行所有业务。

## 3 企业账号登录与 BCrypt

阶段 1 已经把用户密码存为 BCrypt 散列。散列不能被还原为原密码；登录时通过匹配方法判断输入密码是否正确。

阶段 2 将这些数据库用户接入了正式登录流程：

```text
POST /api/auth/login
   ↓
查找账号并匹配密码
   ↓
检查账号是否启用、是否已删除
   ↓
创建登录会话，签发 JWT
   ↓
返回 accessToken、tokenType、expiresIn
```

例如，员工账号存在且密码正确，但已被禁用，仍然不能登录。未知用户名、错误密码、禁用和删除账号统一返回 401，避免通过错误提示探测账号状态。

**有什么用**：数据库用户可以真正登录系统；员工离职或账号停用后，系统能够拒绝其访问。

**后续怎么用**：前端将用户名和密码提交到登录接口，成功后使用令牌调用其他接口。用户 ID 从后端验证的身份中获取，不能直接信任前端填写的“当前用户 ID”。

## 4 JWT 是什么，为什么需要它

JWT 是一种令牌格式。本项目用它携带用户 ID、签发时间、到期时间、发行者和登录会话标识，并用签名防止内容被篡改。

可以把它理解为有有效期的通行证：员工登录后领取通行证，后续办事时出示，服务端检查签名、期限和当前使用资格。

HTTP 的不同请求不会天然知道彼此属于同一次登录。因此前端需要在后续请求中携带凭据。本项目通过请求头发送：

```http
GET /api/auth/me
Authorization: Bearer <登录接口返回的 accessToken>
```

`Bearer` 表示持有该令牌即可用它证明身份，因此令牌需要像密码一样保护，不应写入日志或分享给别人。

本项目 JWT 的角色与权限不写死在令牌中，而是在每次请求时读取数据库。这允许账号权限调整作用于下一次请求。

**有什么用**：后续请求无需反复提交用户名和密码，后端仍能识别访问者。

**需要注意**：JWT 签名不等于加密，令牌内容可能被读取，所以不能把密码或敏感材料放进去。单靠签名检查也不能知道用户是否已退出或被禁用，本项目还会检查数据库状态。

**怎么配置**：`JWT_SECRET` 必须是至少 32 字节随机密钥的 Base64，缺失或长度不够会阻止启动。默认有效期为 900 秒，可通过 `JWT_TTL_SECONDS` 设置为 60–3600 秒；到期后重新登录。配置步骤见 [后端说明](../backend/README.md)。

## 5 Spring Security 如何保护请求

Spring Security 是 Spring 体系的安全框架。它通过过滤器在请求进入 Controller 前检查凭据和接口权限，也支持在方法调用时检查权限。

可以类比 Java 中的方法调用：真正执行业务方法前，先进行一组检查；检查不通过，就直接返回错误，不继续处理业务。

```text
请求进入
   ↓
检查 JWT 签名、发行者和有效期
   ↓
检查会话与账号状态，加载当前角色权限
   ↓
检查接口与方法权限
   ↓
检查目标资源的访问范围
   ↓
执行查询或业务操作
```

本项目使用 Spring Security 的 OAuth2 Resource Server 功能处理 Bearer JWT。这是复用框架的令牌验证能力，当前没有实现第三方 OAuth 登录或独立授权服务器。

**有什么用**：统一处理认证和常见权限判断，业务接口能够复用相同的身份对象与拒绝规则。

**后续怎么用**：新增接口时先定义访问条件，再在 `SecurityConfig` 与方法权限中配置。当前未明确开放的路径默认拒绝，需要随着模块实现补充规则。

## 6 RBAC：用户、角色与权限

RBAC 是基于角色的访问控制。用户拥有角色，角色关联具体权限；用户可以拥有多个角色。

```text
用户 → 用户角色关联 → 角色 → 角色权限关联 → 权限
```

公司里，“管理员”“法务”“员工”是角色，“管理用户”“管理文档”“审查合同”是对应的操作权限。

| 角色 | 当前作用 |
| --- | --- |
| ADMIN | 管理用户、分配角色；读取部门时不限定本人部门 |
| LEGAL | 法务身份，已有文档管理、合同审查等权限定义 |
| EMPLOYEE | 新用户的默认角色，已有制度读取、申请提交等权限定义 |

权限定义存在，不代表对应业务已经完成。文档管理、合同审查和申请提交仍在后续阶段实现。

本项目用户管理方法使用的权限表达式为：

```java
// 项目中的方法授权示例，需要配合已启用的方法安全配置。
@PreAuthorize("hasRole('ADMIN') and hasAuthority('user:manage')")
```

`hasRole` 检查角色，`hasAuthority` 检查具体权限。这个表达式要求同时满足两个条件；即使给 LEGAL 增加 user:manage，也不能通过这里的 ADMIN 角色检查。

**有什么用**：权限可以按岗位统一分配，用户岗位变动时调整角色即可，无需在各个 Controller 中写用户名判断。

**后续怎么用**：在实现文档、审查和审批操作时，为每项操作定义权限，并绑定合适的角色。菜单可以按权限显示，后端仍需独立校验。

## 7 资源权限：为什么还要限制部门和申请

操作权限只说明用户可以使用某种功能。资源权限进一步说明这个功能可以作用于哪些记录。

例如，张三和李四都拥有 EMPLOYEE 角色，也都可以使用申请功能，但这不意味着张三可以把详情接口中的申请 ID 换成李四的 ID 来读取资料。通过修改 ID 访问他人的数据，就是一种越权。

当前规则如下：

| 资源 | 访问范围 |
| --- | --- |
| 部门详情 | ADMIN 可以读取任意部门；其他用户只能读取本人所属部门 |
| 申请基本信息 | 申请人本人，或被明确分配该申请 PENDING 审批任务的用户 |

同部门、拥有 LEGAL 角色或拥有 ADMIN 角色，都不会自动获得全部申请的访问权。待办完成后，基于该待办获得的访问资格结束；申请人本人仍可读取自己的申请。

申请查询在 SQL 中加入当前用户条件，只取授权范围内的记录。无权访问和记录不存在都返回 404，避免泄露其他申请是否存在。

**有什么用**：防止已登录用户读取其他员工的申请和敏感材料。这是企业系统数据隔离的重要基础。

**后续怎么用**：文档下载、附件、AI 检索和分析结果也应校验资源权限。仅隐藏页面按钮无法阻止用户直接请求接口。

## 8 登录会话、退出与禁用

登录会话记录一次登录的使用资格。本项目新增 `auth_session` 表保存会话 UUID、用户 ID、创建时间、到期时间与撤销时间；数据库不保存完整 JWT。

JWT 中的 `jti` 是该会话标识。服务端收到令牌后，用它检查数据库中是否仍有有效会话。

| 操作 | 当前效果 |
| --- | --- |
| 退出登录 | 撤销当前会话，当前令牌不能继续使用 |
| 在两处分别登录，再退出其中一处 | 另一会话仍然有效 |
| 禁用或删除账号 | 撤销该账号全部会话，并拒绝登录 |
| 重新启用账号 | 需要重新登录，旧令牌不会恢复 |
| 修改角色 | 下一次请求读取最新角色和权限 |
| 服务重启且密钥不变 | 有效且未撤销的会话仍可使用 |

如果退出只是前端删除令牌，别人持有的令牌副本可能继续访问。本项目同时在后端撤销会话，因此能够拒绝副本重放。

**有什么用**：使退出、停用账号和调整权限真正影响后端访问资格。

**实现取舍**：每次请求访问数据库，增加查询成本，但便于及时检查账号和权限变化。HTTP 不创建服务端 HttpSession，并不表示系统完全不保存状态；本项目仍在 MySQL 保存登录会话。后续若引入缓存，要同时设计撤销和权限变更的同步机制。

## 9 初始管理员与最后管理员保护

用户管理接口要求管理员身份，因此空库部署需要一个受控的初始入口。

当前初始化器只在显式开启 `INITIAL_ADMIN_ENABLED` 且用户表为空时，根据配置创建管理员。密码使用 BCrypt 保存，没有预设通用密码；已有用户时跳过，服务重启不会覆盖已有密码。

初始化成功后应关闭开关，并清除初始密码配置。阶段 1 的旧库若已有普通用户，不会自动升级为管理员，需要受控分配角色。本次验收只在隔离测试库初始化账号，没有操作实际业务库。

最后一名有效管理员不能被删除、禁用或移除 ADMIN，相关操作返回 409。否则系统可能失去管理用户和恢复权限的入口。

数据库锁用于协调同时发生的管理员变更，锁定读取获取当前管理员集合，避免基于旧快照判断剩余人数。

**有什么用**：既解决首次部署的管理员来源，也保护系统持续可管理。

## 10 接口、错误与代码阅读顺序

| 接口 | 用途 |
| --- | --- |
| POST /api/auth/login | 登录并获得令牌 |
| GET /api/auth/me | 获取当前用户、角色和权限 |
| POST /api/auth/logout | 退出当前登录 |
| GET/POST /api/users | 管理员分页查询、创建用户 |
| GET/PUT/DELETE /api/users/{id} | 管理员查询、更新、删除用户 |
| PUT /api/users/{id}/roles | 管理员整体替换用户角色集合 |
| GET /api/departments/{id} | 按部门范围查询 |
| GET /api/approval-requests/{id} | 按本人或本人待办查询申请基本信息 |

常见错误：401 表示没有有效身份凭据；403 表示身份有效但不满足权限；资源接口可使用 404 隐藏无权访问的数据；409 表示操作与约束冲突，例如移除最后管理员。

建议按以下顺序阅读代码：

| 顺序 | 类 | 重点 |
| --- | --- | --- |
| 1 | AuthController | 登录、身份和退出的请求入口 |
| 2 | AuthService | 密码匹配、创建会话、签发令牌及读取当前权限 |
| 3 | JwtConfig | 密钥、签名与令牌校验规则 |
| 4 | SecurityConfig | 接口匹配、认证过滤链和方法安全开关 |
| 5 | PlatformPrincipal | 当前请求中的用户身份信息 |
| 6 | AdminUserController / UserService | 管理用户、角色变更与管理员保护 |
| 7 | ResourceAccess / ScopedResourceController | 部门判断与申请查询范围 |
| 8 | InitialAdminRunner | 空库首次管理员创建 |

接口字段与配置细节见 [阶段 2 接口与权限说明](../docs/阶段2接口与权限说明.md)。原 `/api/bootstrap/users` 保留用于阶段 1 本地回归，默认关闭；正式账号调用 `/api/users` 使用 Bearer 认证。

## 11 如何验证这些规则

本阶段完整验收包含 12 个测试，全部通过且没有跳过，并验证了打包服务的真实 HTTP 行为。覆盖登录成败、无效与过期令牌、权限刷新、退出撤销、禁用删除、最后管理员保护以及部门和申请访问范围。

例如，一个重要的测试不是只检查员工能读自己的申请，还要检查同部门的其他员工不能读取；管理员能管理用户，也要检查普通员工不能借角色分配接口提升自己。

**有什么用**：权限代码出错时可能产生数据泄露，验证被拒绝的路径和验证成功路径同样必要。

可以在已安装所需 Java、Maven、MySQL 和 PowerShell 的环境中，从项目根目录执行：

```powershell
pwsh -NoProfile -File scripts/verify-stage2.ps1
```

脚本启动独立临时数据库和应用，验证完成后停止自身进程，不修改现有 MySQL 服务。详细范围和证据见 [阶段 2 验收记录](../docs/阶段2验收记录.md)。本笔记整理没有重新运行业务测试。

## 12 与下一阶段的关系

阶段 3 前端登录联调可以直接使用本阶段接口：提交登录 → 获取令牌 → 请求当前身份 → 按角色与权限展示菜单 → 在请求头携带令牌 → 处理 401/403 → 退出时调用撤销接口。

前端提供操作体验，后端承担最终访问校验。用户绕过菜单直接调用接口时，后端也应按照相同规则拒绝。

当前进展：

- 已完成：后端登录、JWT、角色权限、会话撤销、受控用户管理、部门和申请访问边界。
- 后续实现：前端登录与菜单联调、文档与 AI 业务、申请提交和审批流程。
- 尚未实现：刷新令牌、密码重置、登录限流和过期会话清理；正式部署配置也需继续验证。

复习时可以检查自己是否能解释：登录成功为什么不代表能读取所有申请？JWT 有签名为什么还要检查会话？删除页面上的令牌为什么不能替代后端退出？这些判断又如何被后续文档和 AI 模块复用？
