# 阶段 4 学习笔记

主题：制度文档、不可变版本、授权下载与发布留痕  
日期：2026年10月12日

这阶段让制度从“准备好的数据库表”变成可以上传、查询版本、下载和管理访问范围的业务资产，同时建立发布、停用与审计规则。

延续企业办事大厅的类比：前几阶段建好了窗口、通行证和导览屏；阶段 4 建立正式制度档案室。一份制度有固定档案编号，每次修订保存一份新原件，当前执行哪一版由明确的发布记录决定。

## 1 为什么先做文档和版本，再做 OCR 与问答

OCR 是从图片或扫描件中识别文字，RAG 是先检索相关资料再让模型根据资料回答。两者需要知道资料来自哪里、属于哪个版本，以及谁能访问。

```text
阶段 3：登录、菜单、工作空间与公共请求
   ↓
阶段 4：制度原文件、版本、范围、发布和审计
   ↓
阶段 5：提取正文或 OCR，保留页码和来源
   ↓
阶段 6：切片、Embedding 与向量索引
   ↓
阶段 7：有依据、有引用的制度问答
```

例如，模型回答差旅报销规则时，必须使用当前有效版本；员工不能通过提问读到只允许法务访问的制度。仅把若干文本放进模型并不能解决这些问题。

**有什么用**：先明确资料身份、来源和访问边界，后续 AI 功能可以建立在可追溯的数据上。

**当前边界**：本阶段没有实现 OCR、真实向量服务或问答。发布检查已经实现，但新上传版本仍为草稿，必须等后续解析与索引链路就绪才能发布。

## 2 逻辑文档和不可变版本有什么区别

逻辑文档代表一份制度的身份；版本代表这份制度某次修订的原文件与元数据。元数据是描述文件的信息，例如文件名、大小、格式和生效时间。

| 层次 | 保存内容 | 例子 |
| --- | --- | --- |
| document | 名称、创建人、当前版本指针、删除状态 | 员工差旅制度 |
| document_version | 原文件存储键、版本号、散列、有效期、处理与发布状态 | v1.0、v2.0 |

可以类比 Java 中一个稳定的业务 ID 与它的修订记录：申请或引用需要关联具体修订，不能只有一个会不断被覆盖的文件路径。

```text
差旅制度（document）
   ├── v1.0 原文件：保留，已停用
   └── v2.0 原文件：保留，当前发布版本
```

本项目没有覆盖版本文件的接口。内容变化需要上传新版本，同一制度的版本号不能复用；制度名称与访问范围可以编辑并留痕。

**有什么用**：制度修订后仍能核对历史依据，避免旧问答或审批记录指向一份内容已经改变的原文件。

## 3 文件上传为什么使用 Multipart

Multipart 是一种在同一个 HTTP 请求中发送多个部分的格式，适合同时发送文件与结构化信息。

创建制度时发送两个部分：`file` 是文件，`metadata` 是 JSON，包含制度信息和首个版本信息。新增版本只需要该版本的 metadata。

```javascript
// 本项目浏览器页面的核心写法；file 来自文件选择框。
const body = new FormData()
body.append('metadata', new Blob([JSON.stringify(metadata)], {
  type: 'application/json',
}))
body.append('file', file)
await api.post('/documents', body)
```

后端使用 `@RequestPart` 接收文件和 JSON，并校验 DTO。不要把 JSON 当作普通字符串 part 发送，否则类型可能变成 text/plain，后端无法按 JSON DTO 读取。

**有什么用**：一次请求提交制度名称、角色范围、版本号与原文件，失败时统一返回错误。

**后续怎么用**：合同和申请附件也可以采用类似传输方式，但各自仍需独立的业务权限、大小和格式规则。

## 4 为什么既检查扩展名，又检查文件内容

扩展名是文件名末尾的 `.pdf` 等标记，客户端 MIME 是上传方声明的类型。两者都可能被修改，不能只根据其中一个判断文件内容。

| 类型 | 当前检查 |
| --- | --- |
| PDF | 扩展名及 PDF 文件签名 |
| DOCX | ZIP 结构、必须的 XML、Word 正文与类型声明 |
| PNG/JPG/JPEG | 图片实际类型、宽高与可读取性 |

单文件非空且不超过 10 MiB，整个请求不超过 11 MiB。DOCX 解压累计最多 30 MiB、最多 1000 项；禁止危险路径和 VBA 内容。图片最多 4000 万像素。旧版 DOC 需先转换为 DOCX。

DOCX 本质上是包含多个 XML 和资源文件的压缩包。压缩文件本身很小，解压后也可能非常大，所以限制上传大小还不够，需要限制解压后的累计数据。

**有什么用**：避免把改了后缀的普通文本当作制度 PDF，或在处理异常文件时消耗过多资源。

**当前边界**：PDF 签名检查不等于全文解析成功；详细正文提取和解析错误在阶段 5 处理。上传合格仍不能直接进入问答。

## 5 FileStorage 为什么要单独定义接口

FileStorage 是存储抽象：业务只调用存、读和清理方法，不直接绑定某个磁盘目录或对象存储服务。本阶段实现类为 LocalFileStorage。

可以类比 Java 的接口与实现：Controller 和 Service 面向 FileStorage 编程，未来替换成对象存储时，主要实现相同接口，并迁移已有存储键。

```text
DocumentService → FileStorage
                     ↓
              LocalFileStorage
              DOCUMENT_STORAGE_ROOT
```

文件使用服务端随机键保存，例如 UUID 加 `.bin`；原始中文文件名保留在数据库中，下载时再设置。上传文件名不能直接作为磁盘路径，防止 `../` 等路径影响其他文件。

**有什么用**：存储位置与业务职责分离，同时避免把内部磁盘路径作为公共下载地址。

**怎么用**：配置 `DOCUMENT_STORAGE_ROOT`，默认相对 Java 工作目录的 `data/documents`。生产使用固定绝对路径或持久卷，数据库与原文件都要备份；文件不能放进可直接公开读取的静态目录。

## 6 SHA-256 与下载完整性

SHA-256 是对内容计算摘要的方法，相同文件得到相同摘要；本项目在上传时保存摘要，下载时重新计算并核对，同时检查字节数。

它可以类比档案的校验码：有人误替换了磁盘上的文件，数据库里的摘要就与实际文件不一致，系统拒绝返回并提示联系管理员。

它与 BCrypt 的用途不同：BCrypt 用于密码验证，刻意增加计算成本；SHA-256 在这里用于文件完整性检查，不应该拿本项目的文件摘要策略代替密码散列策略。

**有什么用**：防止数据库中的版本信息与实际原文件悄悄失去对应关系。

**后续怎么用**：解析任务也可以按版本和内容摘要确认自己处理的是哪一份不可变文件。摘要只证明内容一致，不能证明制度由谁签发或内容是否合规。

## 7 功能权限和文档范围如何配合

功能权限说明能否使用文档查询或管理；数据范围说明这份具体制度是否允许当前用户访问。

| 场景 | 规则 |
| --- | --- |
| 管理制度 | document:manage，且为本人创建或 ADMIN |
| 普通读取 | document:read，角色命中；有部门限制时还要命中部门 |
| 草稿查看 | 只有具备该制度治理资格的人可以查看 |
| 历史版本下载 | 版本曾发布，且重新满足最新访问范围 |
| 已删除或无权访问 | 统一返回 404 |

例如，只允许 LEGAL 且限财务部门的制度，需要同时满足角色和部门。没有部门配置表示不限制部门；没有角色配置则拒绝普通读取，不推断为全员可见。

法务拥有 document:manage 也不会自动获得所有法务档案的管理权。管理员具有全局治理资格，但员工查询入口仍按制度读取范围筛选。

**有什么用**：避免仅检查“已经登录”就把敏感制度和原文件开放给所有员工。

**后续怎么用**：AI 检索和来源查看都要应用这些条件。前端隐藏按钮不能替代后端校验，已有页面也不能让后续下载跳过重新授权。

## 8 发布状态与处理状态为什么分开

发布状态表示制度是否作为有效规则使用；处理状态表示文件是否完成技术处理。它们不是同一条流程。

| 发布状态 | 含义 |
| --- | --- |
| DRAFT | 草稿，尚未发布 |
| PUBLISHED | 已发布，仍需结合时间和当前指针判断有效性 |
| RETIRED | 已停用，仅保留历史用途 |

处理状态为 PENDING、PROCESSING、READY、FAILED。发布不仅检查 READY，还要求有文本块且全部 INDEXED，文本、向量键和 Embedding 标识非空；Embedding 是将文本转换为用于相似检索的数值表示。

```text
上传 → DRAFT / PENDING
   ↓ 后续解析与索引
处理就绪，但仍是 DRAFT
   ↓ 法务检查并发布
PUBLISHED / READY，成为当前有效版本
```

**有什么用**：防止上传了空内容、解析失败或没有索引的制度直接进入员工问答。

**当前边界**：没有手动将版本标记 READY 的业务入口。本阶段用隔离测试夹具验证发布条件，不代表 OCR 或向量服务已接入。未来版本暂不自动定时发布，尚未生效时发布返回 409。

## 9 事务、行锁与文件回滚

事务让一组数据库操作共同提交或回滚。发布会锁定逻辑制度行，随后停用旧版本、使旧索引 INACTIVE、更新当前版本并写入审计。

可以类比修改档案室“当前执行版本”的登记簿：同一时刻只有一名工作人员能修改该制度的登记行，防止两个发布请求各自认为自己是当前版本。

重复发布同一当前版本为幂等成功，即重复请求不会重复产生效果，也不增加发布记录。不同版本并发发布按锁顺序执行，最终只能有一个当前发布版本。

文件系统不参加 MySQL 事务，所以项目在写入文件后注册事务完成回调：数据库事务失败则删除本次新增原文件。测试会主动回滚，并检查文件和元数据都没有留下。

**有什么用**：避免两个当前有效版本和普通失败上传留下的半成品。

**当前边界**：进程突然崩溃仍可能留下孤立文件。回调不是文件系统与数据库的跨资源原子事务，后续需增加受控清理与恢复机制。

## 10 停用、自然过期和逻辑删除

停用表示结束当前版本的执行资格；自然过期由查询时间判断；逻辑删除表示制度不再开放访问，但保留历史数据。

```text
发布新版：旧版本 RETIRED，旧索引 INACTIVE
停用当前版：清空当前指针，当前索引 INACTIVE
自然过期：有效查询立即排除
删除制度：标记 deleted_at，禁止访问，保留版本与文件
```

历史版本虽然可以在授权后下载，但不能作为当前有效制度查询结果。未来 RAG 不能只看向量库有没有那段文本，还必须校验当前指针、发布状态、时间、处理/索引状态和访问范围。

**有什么用**：制度失效后停止用于当前决策，同时保留未来审计所需的原始依据。

## 12 本次补充：同一个页面组件切换用途时要重新查询

2026年10月12日复核阶段四时，修复了制度管理与制度查询切换后残留上一入口数据的问题。两个路由都使用 `DocumentsView.vue`，Vue 可以复用已挂载的组件，所以 `onMounted` 不一定再次执行。

生活类比：同一个档案窗口从“管理员整理模式”切到“员工查阅模式”，桌上原来摆着的草稿不能继续当作有效制度展示。现在通过 `watch(management, ..., { immediate: true })` 在首次进入和模式变化时重新查询，清空详情、审计、分页和弹窗，同时用请求序号避免旧详情响应重新写回。

它类似 Java 后端同一个 Service 根据查询参数选择治理范围或当前有效范围：对象可以复用，但每次用途改变都要按新条件读取数据。后端继续独立执行权限校验，页面刷新负责保证用户看到的列表与当前入口一致。

**有什么用**：法务上传的草稿在制度管理可见，切到制度查询后不会残留；返回管理可以重新查看并上传新版本。

**后续怎么用**：问答会话、审批列表等页面复用组件时，也要考虑查询条件变化与旧请求返回的顺序。

本次实际重新执行前端构建、21 个后端测试和 11 个 Chromium 用例，全部通过；法务用例包含两入口往返与草稿隔离。详情见 [阶段 4 验收记录](../docs/阶段4验收记录.md) 的本次复核段落。OCR、切片与向量索引仍属于阶段 5/6，发布测试继续使用隔离夹具。
