# 阶段九学习笔记：让差旅申请按已发布流程走到人工结果

日期：2026年10月12日  
主题：流程定义、实例、任务、金额分支、不可变版本、人工状态机与审计。

## 1 阶段目标与生活场景类比

阶段八让员工填单、预审和正式提交；阶段九让指定审批人收到材料、填写意见并作决定。可配置人工审批就是把“哪类申请找谁、按什么顺序、怎样结束”保存为规则，并在每次提交时按规则创建待办。

生活类比：公司公布出差单的盖章路线。小额先找主管，大额再找财务。员工交单时复印一套材料，同时记录当天采用的办事规则版本；后来公司修改路线，窗口不会偷偷更改已经送去盖章的单子。

**有什么用**：员工能看到申请结果，审批人能看到自己的任务，管理员能配置流程，任何处理都有责任人与意见。

## 2 为什么先选型，再配置，最后流转

```text
阶段八：草稿 → 当前内容预审 → 提交快照
阶段九：明确有限范围 → 发布配置 → 固定实例 → 分配任务 → 人工决定 → 留痕
阶段十：在正确状态与事务边界上增加缓存、异步能力
```

先明确“金额区间 + 有序单人节点”，才知道配置如何验证、数据库如何约束；先固定实例，才知道下一任务应该沿用哪条路线。Java 类比：先定义领域规则与输入 DTO，再实现 Service 事务，最后接 Controller 和 Vue 页面。

本阶段选择有限流程方案，复用 Spring 与 MySQL。Flowable 是可执行 BPMN 的流程引擎，适合并行、会签和复杂建模；当前没有这些已确定需求，所以没有引入引擎。当前方案不能被当作完整 BPMN 引擎。

阅读入口：[WorkflowStore.java](../backend/src/main/java/com/enterprise/compliance/request/WorkflowStore.java)、[WorkflowController.java](../backend/src/main/java/com/enterprise/compliance/request/WorkflowController.java)。

## 3 定义、实例与任务分别是什么

| 概念 | 生活类比 | 项目表与例子 |
| --- | --- | --- |
| 流程定义 | 公司公布的办事路线 | workflow_definition：差旅第 1 版 |
| 当前发布指针 | 窗口当前执行哪份规则 | workflow_publication.active_definition_id |
| 流程实例 | 一张出差单实际走的那一次 | workflow_instance：申请 #123、内容版本 3 |
| 审批任务 | 本次轮到谁盖章 | approval_task：主管、处理人、PENDING |
| 动作审计 | 盖章登记簿 | approval_action：处理人、意见、时间、前后状态 |

发布定义不会创建员工任务，员工提交才会创建实例。一个申请退回后可以重提，产生新内容版本和新实例；旧实例仍留在历史。

Java 类比：Config record 是规则 DTO；实例像针对某次业务调用创建的执行上下文；任务像需要人手工执行的工作项。它们是数据库记录，不是 JVM 内存线程。

**后续怎么用**：查询错误时先定位申请版本，再查实例引用的定义和 route_json，最后查任务/动作，不要用“当前配置”解释旧实例。

## 4 金额条件怎样工作

区间下限包含、上限不包含：测试配置 `[0,1000)` 只有主管，`[1000,无上限)` 先主管后财务。999.99 与 1000 会进入不同分支；1000 是可调整的测试示例，不是企业制度。

发布时要求从零开始连续覆盖，不允许缺口、重叠和空节点。金额使用 BigDecimal，比较用 compareTo，避免浮点误差和 0 与 0.00 的小数位差异。每个节点明确指定启用且有 approval:review 的用户。

提交时再检查审批人资格，且整条路线不能包含申请人。没有流程或审批人失效时明确失败，不会把申请自动批准。

**有什么用**：条件来自已发布配置，员工无法在请求体里随意指定自己的审批人。

## 5 为什么已运行流程固定版本

流程发布创建新 workflow_definition，更新当前指针；实例保存 definition_id、route_json、request_content_version 与 request_snapshot。管理员发布第 2 版后，第 1 版实例继续按原路线走；新提交使用第 2 版。

生活类比：每张单子附上当时的盖章路线，不能用今天的新规则解释昨天的处理。

Java 类比：像不可变配置对象与调用时的快照。数据库保留版本比在全局变量中覆盖配置更可靠，重启后仍能解释处理过程。

代码阅读：WorkflowStore.publish → TravelStore.submit → WorkflowStore.start → WorkflowStore.decide。

## 6 人工状态机与退回恢复

状态机就是为每个当前状态规定允许发生的动作。

| 当前状态 | 操作 | 结果 |
| --- | --- | --- |
| DRAFT | 提交 | IN_REVIEW，保存快照与首个任务 |
| IN_REVIEW | 同意 | 下一节点或 APPROVED |
| IN_REVIEW | 拒绝 | REJECTED |
| IN_REVIEW | 退回 | RETURNED |
| IN_REVIEW / 历史 SUBMITTED | 申请人撤回 | WITHDRAWN，待办取消 |
| RETURNED / WITHDRAWN | 重新编辑 | DRAFT、内容版本 +1、预审 STALE |

退回不会直接改为可编辑旧草稿，必须点击“重新编辑并预审”。新材料必须重新预审、确认、提交；原 request_submission 不覆盖。AI 预审状态与人工状态分开，UNKNOWN 也可以交给人工决定，模型失败不变成人工批准。

**后续怎么用**：扩展新的动作时，先定义允许状态和恢复路径，再编写事务代码与并发测试。

## 7 权限、行锁与版本怎样配合

功能权限回答“你是否有审批功能”；任务归属回答“这件任务是否分配给你”。管理员也不能处理别人的任务。历史任务参与人能看历史，但材料与附件限制到自己收到的提交快照；退回后员工新增的未提交材料不对旧审批人开放。

处理事务先 `SELECT ... FOR UPDATE` 锁申请行，再锁任务，检查 PENDING 和 lockVersion，再更新任务、申请、下一节点和审计。锁让并发操作排队，版本让旧页面明确失败，唯一约束防止重复实例或节点。

生活类比：两个人同时操作同一纸质单，窗口先把单子交给其中一人；第二个人拿到时必须重新核对它是否已经盖章或撤回。

项目例子：同意与撤回同时请求，只有一个成功；另外一个读到最终状态后返回 409。测试使用真实 MySQL 的两个线程，而不是只检查按钮禁用。

**有什么用**：服务重启、多窗口、重复点击以及直接调用 API 都不能绕过数据库一致性约束。

## 8 怎么使用与阅读代码

1. 管理员打开“审批流程配置”，选择审批人、设置区间和节点，发布版本。
2. 员工保存差旅草稿、附件、预审，确认当前内容提交。
3. 审批人打开“审批中心”，查看固定提交材料、授权范围内的预审与附件，填写意见。
4. 员工查看结果和历史；退回/撤回后重新编辑、预审、提交。

## 9 实际验证与当前边界

本轮实际执行前端构建和阶段九验收脚本，空库九次迁移、58 个后端测试、8 个浏览器用例通过；13 个其他阶段浏览器用例按配置跳过。真实 MySQL 验证金额边界、固定版本、并发发布与 RR 当前读取、并发审批与撤回、旧材料范围；浏览器验证发布 → 退回 → 重新编辑/预审/提交 → 人工同意，并检查桌面/移动截图。详细证据与未覆盖范围见 [阶段九验收记录](../docs/阶段9验收记录.md)。本阶段工程验收关闭真实生成端，保留 UNKNOWN 并由人工决定，不替代真实模型质量评估。

尚不支持并行、会签、任务转派、自动批准、BPMN 和旧实例迁移；下一审批人停用会阻止流转，管理员恢复账号/权限后重试。旧 SUBMITTED 可撤回重提，不自动套用新配置。历史列表与材料预审有查询窗口，超大历史、生产部署和已有业务库升级后续完善。历史阶段笔记保留其当时语境。

阶段十可以在这些已明确的事务边界上加入异步通知或缓存；缓存必须重新校验任务归属、状态和版本，消息失败不能丢失已保存待办。
