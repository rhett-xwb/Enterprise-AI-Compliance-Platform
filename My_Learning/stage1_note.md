# 阶段 1 学习笔记

主题：数据库与工程骨架  
日期：2026年10月11日

这阶段完成的是后端基础建设：让项目能够启动、连接数据库、处理请求，并安全地完成用户增删改查。

可以把它理解成开一家企业办事大厅：先划分办公区域、建立档案、规定窗口办事流程，再开展制度查询和审批业务。

## 1 项目目录划分

| 目录 | 用途 |
| --- | --- |
| frontend | 用户看到和操作的页面 |
| backend | 处理业务、权限和数据库读写 |
| ai-service | 后续实现文档解析与 OCR，目前仅为规划目录 |
| docs | 保存设计、计划、接口说明和开发日志 |
| docker | 保存部署配置 |

**有什么用**：让代码职责清楚。后续开发 OCR、审批或页面时，能够明确代码放在哪里，避免不同职责混在一起。

## 2 Spring Boot 后端与分层

Spring Boot 提供 Java 后端的运行基础。用户模块按以下结构组织：

```text
前端请求
   ↓
Controller 接收请求、检查参数
   ↓
Service 执行业务规则
   ↓
Mapper 读写 MySQL
   ↓
返回处理结果
```

| 层次 | 职责 | 新增员工的例子 |
| --- | --- | --- |
| Controller | 接收 HTTP 请求，校验参数，返回结果 | 接收用户名、密码和员工信息 |
| Service | 实现业务规则与事务 | 检查部门、处理密码、关联员工角色 |
| Mapper | 执行数据库读写 | 将用户记录存入 MySQL |
| Entity | 对应数据库记录 | 表达用户表的字段 |
| DTO | 表达接口输入与输出 | 创建请求包含密码，返回结果排除密码 |

**有什么用**：修改新增员工的业务规则时，主要修改 Service；修改页面展示时，不必跟着修改数据库操作。接口数据也不必完全等同于数据库字段。

**后续怎么用**：文档管理、申请和审批模块可以沿用这种分层方式，在各自 Service 中实现业务规则。

## 3 数据库结构与 ER 关系

ER 关系描述数据实体之间的关联，例如一个文档可以有多个版本，一个用户可以有多个角色。

阶段 1 建立了 22 张基础表，覆盖用户与权限、文档与版本、申请与审批、问答与引用等数据。

```text
用户 ← 用户角色关联 → 角色
文档 → 多个文档版本 → 多个文本块
申请 → 审批实例 → 审批任务
```

例如，后续 AI 引用某条制度时，需要找到具体文本块，再追溯到文档版本。审批任务也需要知道属于哪份申请、由谁处理。

**有什么用**：提前明确数据如何关联，避免后续模块各存各的数据却无法追溯来源。

**当前边界**：建表表示存储结构已准备好，文档、问答和审批业务仍需后续实现。具体表与关系见 [数据库设计](../docs/数据库设计.md)。

## 4 Flyway 数据库迁移

Flyway 是管理数据库结构版本的工具，可以理解为数据库的升级记录。

| 迁移版本 | 当前作用 |
| --- | --- |
| V1 | 创建基础表 |
| V2 | 初始化角色、权限及其关联，不创建默认账号密码 |

应用启动时检查迁移历史，只执行尚未执行的迁移。以后增加字段，可以新增 V3，而不需要每个人手动修改数据库。

**有什么用**：新环境初始化、团队协作和部署升级时，数据库变更有记录且能够按顺序执行。

**后续怎么用**：已经应用的迁移不随意修改。新增结构变化使用更高版本迁移，并先验证。当前配置禁止 Flyway clean，也不自动跳过非空数据库的初始化检查。

## 5 用户 CRUD 与软删除

CRUD 指新增、查询、修改、删除。目前用户模块支持创建用户、分页查询、更新资料和软删除。

| 操作 | 请求方式 | 接口 |
| --- | --- | --- |
| 新增 | POST | /api/bootstrap/users |
| 列表 | GET | /api/bootstrap/users?page=1&size=20 |
| 详情 | GET | /api/bootstrap/users/{id} |
| 更新 | PUT | /api/bootstrap/users/{id} |
| 删除 | DELETE | /api/bootstrap/users/{id} |

软删除是保留数据库记录，并标记为已删除。本项目删除用户时还会禁用账号、清除角色关联；删除后列表不再显示该用户，详情返回 404，用户名不复用。

例如员工离职后，账号不能继续使用，但未来的历史申请仍能关联到这个人。

**有什么用**：验证请求进入、规则执行、数据写入和结果返回的完整链路；软删除也为历史审计保留关联信息。

接口字段与请求示例见 [阶段 1 接口规范](../docs/阶段1接口规范.md)。

## 6 密码与访问保护

### BCrypt 密码散列

BCrypt 将密码处理为不可逆的散列值。后续验证输入密码时进行匹配，而不是还原原密码。

```text
创建用户：输入密码 → BCrypt 处理 → 保存散列
验证密码：输入密码 + 已存散列 → 判断是否匹配
```

当前用户返回 DTO 不包含明文密码或散列。密码至少 12 字符，且不能超过 72 UTF-8 字节；字节限制需要特别注意中文等字符。

**有什么用**：数据库不直接保存明文密码，接口也不会把密码信息发送给前端。

### 临时本地认证

业务接口默认关闭。只有显式开启本地模式，并提供临时管理员凭据，才能验证 CRUD；该模式要求应用监听本机回环地址。

临时管理员通过 HTTP Basic 认证，账号保存在内存中。数据库中的普通用户目前不能通过这套临时认证登录。

**有什么用**：在正式权限系统完成前，为开发阶段的读写接口提供访问保护。

**当前边界**：这不是完整的企业登录系统。企业账号认证、JWT 和正式 RBAC 留待阶段 2 实现。

## 7 统一返回 异常处理与日志

### 统一响应

接口采用一致的返回格式：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

`code` 表示结果，`message` 提供说明，`data` 保存实际数据。当前成功 code 为 0，错误 code 与 HTTP 状态码一致。

**有什么用**：前端可以统一处理成功和失败，不必为每个接口重新编写不同的判断方式。

### 统一异常处理

| 场景 | 常见 HTTP 状态 |
| --- | --- |
| 参数不符合要求 | 400 |
| 未认证或凭据错误 | 401 |
| 已认证但无权限 | 403 |
| 用户不存在或已删除 | 404 |
| 用户名重复或数据冲突 | 409 |

**有什么用**：让错误可识别、可处理，同时避免把 SQL、堆栈或密码直接返回给前端。

### 请求日志

日志记录请求标识、请求方法、状态和耗时。请求标识通过 `X-Request-Id` 返回，不记录密码、认证头或请求正文。

例如员工反馈某次操作失败，可以通过请求标识查找对应日志，帮助定位问题。

**有什么用**：在联调和排查故障时，能够追踪一次请求，而不是只能凭页面提示猜测原因。

## 8 配置与运行说明

数据库连接、端口和临时认证开关通过配置与环境变量管理。环境示例放在根目录 `.env.example`，真实凭据不提交版本库。

**有什么用**：不同电脑可以使用不同的数据库账号、端口和密码，而不必修改业务代码。

Spring Boot 不会自动读取项目根目录的 `.env`，启动时需要通过进程环境变量或 IDE 运行配置注入。后端启动步骤见 [后端说明](../backend/README.md)。

MySQL Compose 配置已经提供，但本阶段未验证容器启动；真实数据库验收使用的是独立的本机 MySQL 实例。

## 9 真实 MySQL 验收

阶段 1 使用独立空数据库执行迁移，7 个测试全部通过且没有跳过。打包后的应用也完成真实 HTTP 新增、查询、修改、删除和默认拒绝访问检查。

测试覆盖密码散列、参数校验、用户名冲突、权限保护、软删除及部分数据库关系约束。

测试过程中发现：混用 JDBC 更新与 MyBatis 查询时，同一事务中的查询可能读取到旧缓存。已将用户更新与软删除统一通过 MyBatis 执行，使缓存正确失效，并通过重测。

**有什么用**：验证工程能够在真实数据库上工作，而不只是代码可以编译；也能提前发现数据一致性问题。

完整证据见 [阶段 1 验收记录](../docs/阶段1验收记录.md)。后续可以从项目根目录重新执行：

```powershell
pwsh -NoProfile -File scripts/verify-stage1.ps1
```

脚本启动独立临时数据库和应用，完成检查后停止自身进程，不修改现有 MySQL 服务。
